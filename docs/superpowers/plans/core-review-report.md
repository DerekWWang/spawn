## Important behavioral findings

1. **Death deletes equipped clothing under both inventory policies.** `SurvivalEvents.java:186-187` copies state only for non-death clones. Garments exist only as strings in the old body's state, and no death/drop handler converts them back to stacks or transfers them when keep-inventory is enabled. Equip clothing, die, and respawn: it is neither retained nor dropped. Minecraft's `ServerPlayer.restoreFrom` transfers normal inventory but only specially marked persistent data, not this state. Reset anatomy/immunity independently from clothing inventory handling.

2. **Swapping garments launders all durability and item components.** `SurvivalApi.java:104-105` returns a brand-new stack of the old garment, saves only the new item's ID, and sets wear to zero. Swap a nearly exhausted jacket for another, then swap back: both become unworn; dye/custom metadata is also lost. Persist actual garment stacks or transfer their wear/components through equip and unequip.

3. **The public eat action bypasses consumption time and vanilla item semantics.** `SurvivalApi.java:88-90` immediately adds nutrition and shrinks the stack, with no capacity check, pending action, or cooldown. Any ordinary player can repeatedly call `/survival act eat`, while bots use the same shortcut. Stew loses its bowl; food consume effects are skipped. The local `Consumable` implementation normally enforces `consumeTicks`, invokes consume effects/listeners, and applies consumption/remainder behavior. Route all controllers through a shared timed consumption path that still grants nutrition once.

4. **Cake is consumed but grants no persistent nutrition.** `SurvivalEvents.java:158-163` credits only `LivingEntityUseItemEvent.Finish`, while `SurvivalApi.java:112` overwrites vanilla hunger from survival state. Local `CakeBlock.java:85` feeds `FoodData` directly and emits no use-item finish. A hungry player eats a slice, briefly gains vanilla hunger, then loses that gain at the next physiology sync. Add coverage for direct food paths; ordinary item consumption itself does not appear double-counted because Finish runs after vanilla consumption and sync overwrites the vanilla result.

5. **Climbing straight upward costs idle hunger/thirst.** `SurvivalEvents.java:43-49` detects movement using only X/Z displacement, then requires that flag for `onClimbable()`. Climb a vertical ladder while holding X/Z fixed: the activity is IDLE rather than the specified 5x climbing rate. Include vertical motion in climbing detection, without treating falls as climbs.

6. **Configured daily recreation duration applies only to the first day.** `SurvivalApi.java:38` prorates the configured requirement, but `SurvivalState.java:121` resets every later day's quota to 4500. Set recreationHours to 4 or 5 and cross a day boundary: the requirement silently returns to 4.5 hours. Keep the configured full-day quota in the simulation input/state.

7. **Respiratory disease timings do not match the approved strain.** `SurvivalState.java:44,60` initializes 54000 ticks and enables symptoms only below 42000. That means just over 12 hours of incubation and just under 42 hours of symptoms, instead of 6 hours and two days. Use explicit incubation and symptom durations rather than mismatched remaining-time constants; add onset/boundary assertions.

8. **Human and NPC water consumption have different infection outcomes.** `SurvivalApi.java:131-132` can transmit the systemic strain through contaminated water, but `SurvivalEvents.java:119-124,162` (NPC vessel/source drinking and normal water-bottle use) only sets poisoning. These paths also assign poisonTicks=6000 and can shorten an existing longer poisoning condition, whereas the API preserves the larger duration. Route all water intake through the same contamination function. A script calling `act(drink)` and an NPC autonomously drinking the same untreated water must have equivalent disease rolls.

9. **Offhand interaction validates one stack but consumes/uses the main hand.** `SurvivalEvents.java:168-182` chooses treatment/clothing from `e.getItemStack()`, then `SurvivalApi.java:54` always loads `actor.getMainHandItem()`. With a bandage in the offhand and a painkiller in the main hand, offhand treatment applies/consumes the painkiller; with an empty main hand it fails even though the clicked hand has the supply. Pass the actual hand/stack through the shared action API and test both hands.

10. **Sleep catch-up assigns sleeping costs by controller class, not actual activity.** `SurvivalEvents.java:201` calls `advance(..., actor instanceof Player)`. With a reduced sleeping-player percentage, every awake player gets half-rate sleeping expenditure, while an actually sleeping villager gets full idle expenditure. It also bypasses NEEDS_RATE, unlike the normal update at `:62`. Capture each entity's relevant sleeping/activity state before vanilla wakes sleepers and use a consistent time-scaling policy.

11. **Server season configuration is not synchronized to clients.** `spawn_9b5fbb9.java:14` registers all configuration as LOCAL; snapshots at `SurvivalNetwork.java:17-23` send only calendar ticks. `SurvivalHud.java:28,46` derives the season label through `SurvivalCommands.calendarText`, which reads the client's local SEASON_DAYS. On a dedicated server with seasonDays=14 and a default client=28, the HUD reports Spring while server crop/climate rules use Summer. Send the calendar interpretation/configuration or server-computed season/day with the snapshot. Keep the HUD preference local separately.

## Important remaining spec gaps

- **Clothing visuals and inspection:** the only clothing client implementation is text in `SurvivalHud`; there is no garment rendering layer, tracked-entity garment state, durability display, body diagram, or nearby full health/clothing screen. Self snapshots cannot support seeing other players/NPCs wearing garments.
- **NPC work and care parity:** `autonomy` stops navigation once every 100 ticks at zero mental capacity but does not suspend vanilla goals/brain work or scale their cadence. It seeks food/water/company but does not treat illnesses using supplies or equip clothes. The shared API offers no nearby-target clothing action or ownership check.
- **Temperature model:** insulation only reduces cold loss (`SurvivalState.java:90-94`); wool has no heat/breathability cost. Thirst exposure uses ambient alone, before shelter/wetness adjustments. Thermal recovery immediately clears its timer on crossing 35/40 rather than sustained recovery. These are central requested interactions, not merely missing polish.
- **Data/config coverage:** humanoid membership is hardcoded plus a persistent enrollment flag; disease strains, durations, contamination rates, basal rates, and thermal thresholds are hardcoded. Pathogen-specific definitions and the planned configurable rates/thresholds are absent.
- **Damage localization:** injuries use global post-armor damage and a random body region, with only a high-projectile/fall special case. Attack direction and armor coverage by injured region are absent; hearing has no injury path or gameplay consequence.
- **Verification does not establish persistence or multiplayer:** `SurvivalGameTests.java:58` labels a same-entity encode/read round trip as persistence; `controllerParity` inspects two detached state values and enrollment, not matching timed actions or actual entity expenditure. No tests cover death/keep-inventory, disk reload, clone/dimension travel, sleep, food finish/cake, offhand validation, clothed remote entities, or two-client server synchronization. The 21 pure assertions do not close these integration gaps.

No unsupported client-to-server mutation packet was found: current custom networking is a bounded server-to-client snapshot. Operator controller commands are permission-gated. Those facts do not substitute for the multiplayer acceptance tests above.

## Follow-up checks requested by implementer

- Sleep accounting has an additional one-tick undercount at `SurvivalEvents.java:196`: subtracting `sleepBefore` already isolates the adjustment. Local `MinecraftServer.java:1103` advances clocks before calling `level.tick` at line 1123; the sleep event is within that level tick immediately before the clock adjustment. No further regular clock tick occurs before ServerTick.Post, so the extra `-1` is incorrect.
- Current version-1 serialization has no observed round-trip field-order mismatch. Any new garment-stack/quota fields need a new encoder version and explicit legacy-v1 decoding; simply changing the field order or rejecting v1 will reset existing bodies and lose clothing. The old garment encoding is four repetitions of UTF registry ID followed by long wear ticks.
